## 明细

### DEF-001 · 非持久帧未发送(P0)
- **日期**:2026-10-27
- **现象**:daemon 日志显示已连接,但服务端 6 分钟收到 0 条 `inbound HEARTBEAT`;Redis `agent:execs:{agentId}` 永为空;调度器持续 `NO_EXECUTOR_ONLINE`,任务无人认领。
- **根因**:`send_frame(durable=False)` 分支只把 outbox_id 置 None 后调用 `_flush_one(None)`,后者开头即 return——"非持久"被实现成了"不发送"。**为什么会写错**:把 outbox(持久化)与"发送动作"耦合进了同一条路径,只想着跳过落库,忘了发送本身。
- **修复**:`send_frame` 对非持久帧走 `_send_now` 直发路径;持久帧照旧落库+flush。
- **回归**:重启 daemon 后服务端日志出现 `inbound HEARTBEAT executorId=10000`,Redis `agent:execs:10001={10000}`,dispatch 10000/10001 均被领取并 SUCCEEDED。
- **状态**:已修复(已回归)

### DEF-002 · 空闲读超时误判断线(P1)
- **日期**:2026-10-27
- **现象**:每 60s 出现 `ws.closed: socket error: timed out` 并立刻重连;会话被反复重建。
- **根因**:协议中数据流是单向为主(执行器→服务端),无下行帧时读循环必然超时;把手写 WS 客户端里统一的"超时=断线"假设带进了 runtime,未区分"读空闲"与"连接死亡"。
- **修复**:新增 `WsIdleTimeout`(继承 WsClosed);主循环捕获后 `continue` 保持会话;真正的 close/OSError 仍触发退避重连。
- **回归**:修复后连接稳定无重连,心跳计数持续增长,派发正常。
- **状态**:已修复(已回归)

### DEF-003 · 同一 token 双 daemon 互踢(P2)
- **日期**:2026-10-27
- **现象**:两个 daemon 进程并存时互相报 `server closed: executor connection replaced`,连接抖动。
- **根因**:服务端按 executorId 维护单会话(新连接顶掉旧连接),属协议设计而非 bug;缺陷在于我们的部署/测试脚本未做单实例保障,旧进程未被清理。
- **缓解**:运行约定"同 executorId+token 仅一个实例";启动前 `pkill` 清场;已写入 README 与 00 号规范 §4。P1 可在 daemon 内加 pid 锁文件。
- **状态**:已缓解(有约束)

### DEF-004 · 测试回声服务缺陷(P2)
- **日期**:2026-10-27
- **现象**:WS 单测首帧回显是掩码字节;300KB 大帧回显时服务端线程静默死亡,客户端读超时 60s。
- **根因**:①测试服务端收到客户端掩码帧后未去掩码就回显;②回显大帧时用 `struct.pack(">H", 300001)` 超 16 位长度上限抛 `struct.error`,且整段读帧逻辑未处理 TCP 分包(8 字节长度头可能分次到达)。教训:测试桩的协议正确性与被测端同等重要。
- **修复**:测试服务端补去掩码与 `_recv_all` 定长读取;长度编码按 126/127 分档。
- **回归**:31 个单测全绿,含 300KB 大帧往返断言。
- **状态**:已修复(已回归)

### DEF-007 · 恢复逻辑在每次重连时执行,误杀健康运行中的任务(P0)
- **日期**:2026-10-27(抽奖工单 10003 联调发现)
- **现象**:工单 10003 执行 3 分钟后,服务端 dispatch 置 FAILED,`error="runtime restarted mid-dispatch"`;runtime 侧 claude 实际成功完成并上报 `success=true`,被服务端以 `TERMINAL_FAILED` 拒收。
- **根因**:`_recover()` 放在了重连循环内——连接每次抖动都会把数据库中"非终态"的运行标记为失败,而此时 worker 线程还活着。**为什么会写错**:把"进程启动时的恢复"误设计成"连接建立时的恢复",混淆了进程生命周期与连接生命周期。
- **修复**:recovery 只在 daemon 进程首次连接时执行一次(`recovery_done` 标志);重连只做 replay_pending。
- **回归**:待工单 10004 全流程验证。
- **状态**:已修复(已回归)

### DEF-008 · 心跳线程随重连泄漏(P1)
- **日期**:2026-10-27(与 DEF-007 同窗口发现)
- **现象**:服务端同 1 秒内收到 4 条心跳(正常应 30s 一条);来源是历次重连各自 `new Thread` 且永不退出,泄漏线程共用当前 ws 发送。
- **根因**:心跳线程生命周期绑定在了连接循环而非进程;`_stop` 只在进程退出时置位。
- **修复**:`_start_heartbeat_once()` 保证每进程一个心跳线程。
- **回归**:与 DEF-007 一并回归通过。
- **状态**:已修复(已回归)

### DEF-009 · 超时杀树误杀 daemon 自身进程组(P0,T-C2 发现)
- **日期**:2026-10-27
- **现象**:20s 超时保险丝触发瞬间,daemon 进程无声死亡(无 traceback),dispatch 10009 永久 RUNNING,服务端 presence 过期。
- **根因**:Popen 未设 `start_new_session`,claude 子进程与 daemon 同进程组;超时 watcher 执行 `os.killpg(os.getpgid(proc.pid))` 等价于 `killpg(daemon 自己的组)`。**为什么会写错**:照搬上游 Java CliExecutor 的"杀进程树"语义,忽略了 POSIX 进程组继承——子进程默认不换组。
- **修复**:Popen 增加 `start_new_session=True`,killpg 只命中 claude 树。
- **回归**:T-C2b 超时触发、claude 树被杀、daemon 存活、FAILED 上报。
- **状态**:已修复(已回归)
